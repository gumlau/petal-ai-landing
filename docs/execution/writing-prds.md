# PRD 写作指南 - Petal GTD 应用分析

> 对应技能：`.claude/skills/writing-prds/SKILL.md`

## 概述

产品需求文档（PRD，Product Requirements Document）是产品开发过程中的核心文档，用于定义要构建的产品功能、解决的问题和成功标准。对于 Petal GTD 这样的独立开发项目，PRD 的作用不仅是与团队沟通（即使团队只有一个人），更是帮助开发者理清思路、保持聚焦、避免功能蔓延的工具。

本文档基于 11 位产品领导者的 14 条洞察，总结 PRD 写作的核心原则，并提供适合独立开发者的简化模板。特别讨论 AI 时代 PRD 的变化——从"文档优先"到"原型优先"的转变。

## 核心原则

基于 `.claude/skills/writing-prds/SKILL.md` 的核心洞察：

### 1. 以问题和背景开篇，而非解决方案

> "文档中最重要的部分是开头——什么是背景和上下文？问题是什么？为什么重要？为什么现在重要？" —— Maggie Crowley

许多 PRD 的常见错误是直接跳到功能描述。正确的做法是先让读者（包括未来的自己）理解**为什么**要做这件事。一个好的 PRD 开头应该回答：

- 用户遇到了什么问题？
- 这个问题有多痛苦/频繁？
- 为什么是现在解决，而不是更早或更晚？

### 2. PR/FAQ 格式强制清晰思考

> "每当我们设计新产品时，我们会先写一份新闻稿，用一种能让客户和外部世界产生共鸣的方式描述它。这个想法必须跃然纸上。" —— Bill Carr

亚马逊的逆向工作法（Working Backwards）使用假想的新闻稿来验证产品想法。这个方法的价值在于：

- 强制你用用户语言描述产品价值
- 如果写不出让人兴奋的新闻稿，说明产品定位不够清晰
- PR/FAQ 可以作为过滤机制，从多个想法中筛选最好的

### 3. AI 时代：Demo 优先于 Memo

> "在这个时代，如果你不通过原型和构建来看你想要构建什么，那就做错了。Prompt sets 是新的 PRD。" —— Aparna Chennapragada

这是 AI 时代最重要的转变：

- 传统 PRD：详细描述 → 设计稿 → 开发
- AI 时代：快速原型 → 验证 → 迭代 → 正式开发

对于 AI 功能，prompt sets 和工作原型比文字描述更有效。v0、Replit 等工具让"Live PRD"成为可能——交互式、动画化的原型替代静态文档。

### 4. Evals 作为活的 PRD

> "这就是产品需求文档应该有的最纯粹形式——这个 eval 评判器告诉你它应该是什么，而且是自动的、持续运行的。" —— Hamel Husain & Shreya Shankar

对于 AI 产品，可执行的评估测试（evals）比静态文档更能定义产品需求：

- Eval 是自动验证的 PRD
- 失败的 eval 暴露不满足的需求
- 需求会随真实数据演进，eval 可以持续更新

### 5. 保持轻量以便行动

> "除非是非常复杂的功能，我们的 PRD 都尽量保持简洁。我只想要最少的上下文来确保团队在同一页面上，确保关键结果在交付时会存在。" —— Eric Simons

独立开发者的 PRD 更应该轻量：

- 长达 30 页的 PRD 没人会读
- 聚焦于"关键结果"（key outcomes），而非每个细节
- PRD 的目的是指导行动，不是详尽记录

### 6. PRD 展示专业素养

> "你的 PRD 质量够好吗？你写的草稿会分发给客服团队、营销团队吗？你必须通过你的产出物产生影响。" —— Vikrama Dhiman

即使是独立开发者，高质量的 PRD 也有价值：

- 证明你认真思考过问题
- 帮助未来的自己（或潜在的合作者）理解决策
- 职业发展中，PRD 是展示专业能力的重要证据

### 7. AI 可以辅助 PRD 写作

> "我用 ChatGPT 和一个提示词，为这个非常技术化的产品生成了一份非常可用的 PRD 规格。" —— Claire Vo

AI 在 PRD 写作中的作用：

- 生成用户故事、范围定义等基础内容
- 从粗略笔记或语音转录生成结构化 PRD
- 让 PM 可以专注于高层战略和叙事

但注意：AI 生成的 PRD 需要人类审核和调整，尤其是产品定位和战略决策。

## Petal GTD 现状分析

### 当前项目的 PRD 写作模式

分析当前项目中的 PRD（`tasks/prd-product-docs.md`），可以观察到以下模式：

**优点**：
- 结构清晰：Introduction → Goals → User Stories → Requirements → Non-Goals
- User Stories 有明确的 Acceptance Criteria
- 有 Technical Considerations 和 Design Considerations 部分
- 包含 Open Questions 保持开放性

**可改进点**：
- "Why Now" 部分不够明确——为什么要现在写这些文档？
- 缺少成功指标的量化定义
- User Stories 数量较多（24个），可能需要更明确的优先级排序

### 独立开发者场景的特殊考虑

对于 Petal GTD 这样的独立项目，PRD 的作用有所不同：

1. **读者主要是自己**：不需要说服利益相关者，但需要帮助未来的自己记住决策原因
2. **迭代速度快**：PRD 应该足够轻量，能快速更新
3. **资源有限**：PRD 应该帮助聚焦，而非扩展范围
4. **一人多角色**：PRD 需要同时考虑产品、设计、开发视角

## 关键洞察

### 洞察 1：PRD 的核心目的是对齐，而非记录

PRD 不是为了详尽记录每个细节，而是为了：
- 让自己在开发前理清思路
- 让未来的自己理解当时的决策
- （如有）让团队成员对齐理解

如果 PRD 写完后没人再看，说明它没有达到目的。

### 洞察 2：原型是最好的 PRD

对于 UI 功能和 AI 功能，一个可交互的原型比 10 页文档更有效：

- Guillermo Rauch 描述的"Live PRD"：产品团队在 v0 中构建了新功能的完整交互原型，所有人看完后说"直接发布吧，没什么好讨论的了"
- 原型消除歧义，文字描述总是留有解释空间

### 洞察 3：AI 时代 PRD 写作变成核心技能

> "在 Claude Code 的世界里，你不怎么写代码，你花大量时间写 PRD... 你可以花点时间写一个提示词，把你的碎片想法转化为 PRD。" —— Dan Shipper

当 AI 可以帮助写代码时，"定义要做什么"变得比"如何做"更重要。PRD 写作能力成为核心竞争力。

### 洞察 4：失败的 PRD 都缺少"Why Now"

分析失败的产品项目，常见问题是无法回答"为什么是现在"：

- 如果没有紧迫感，优先级会被质疑
- 如果任何时候都可以做，说明可能不那么重要
- "Why Now" 帮助筛选真正值得投入的功能

### 洞察 5：PRD 是决策日志，不是规格说明

好的 PRD 应该记录：
- 考虑过哪些选项
- 为什么选择了这个方案
- 放弃的方案有什么问题

这样未来回顾时可以理解决策逻辑，避免重复讨论。

## 行动建议

### 适合独立开发者的简化 PRD 模板

```markdown
# [功能名称]

## 问题（Why）
- 用户遇到什么问题？
- 这个问题有多痛苦？（频率 × 严重程度）
- 为什么是现在解决？

## 解决方案（What）
- 一句话描述解决方案
- 用户使用后会说什么？（客户引述）
- 明确不做什么（Out of Scope）

## 成功标准（How We Know）
- 定量指标：什么数字变化说明成功？
- 定性信号：用户会有什么行为变化？

## 关键决策
- 方案 A vs 方案 B：选择了 A，因为...
- 争议点：如何处理了...

## 原型/Demo
- [链接到 Figma/v0/Replit 原型]
- 截图或 GIF 展示核心交互

## 验收标准
- [ ] 具体的可验证条件 1
- [ ] 具体的可验证条件 2
```

### AI 时代的 PRD 工作流程

1. **碎片想法阶段**
   - 用语音备忘录记录想法
   - 让 AI 将语音转录整理成结构化笔记

2. **原型阶段**
   - 用 v0/Replit 快速构建可交互原型
   - 原型即 PRD，展示核心交互

3. **验证阶段**
   - 内部 dogfooding 测试原型
   - 收集反馈，迭代原型

4. **正式化阶段**
   - 只有确定要开发时才写正式 PRD
   - PRD 聚焦于决策记录和验收标准

### 短期行动（1-2 周）

1. **建立 PRD 模板**
   - 创建 `templates/prd-template.md` 文件
   - 包含上述简化模板

2. **回顾现有 PRD**
   - 检查 `tasks/prd-product-docs.md` 是否有明确的"Why Now"
   - 补充缺失的成功标准定义

### 中期行动（1-2 月）

1. **尝试 Live PRD**
   - 下一个 UI 功能用 v0 或 Figma 原型替代文字描述
   - 评估原型 vs 文档的效率差异

2. **建立 PRD 归档**
   - 完成的功能 PRD 归档到 `docs/prds/` 目录
   - 保留决策历史供未来参考

### 长期行动（季度）

1. **评估 PRD 有效性**
   - 回顾哪些 PRD 真正指导了开发
   - 哪些 PRD 写完后再没看过
   - 迭代模板和流程

2. **探索 AI Evals**
   - 如果开发 AI 功能，尝试用 eval 定义产品需求
   - 将关键用户体验转化为可自动化测试的标准

## 思考问题

1. **如果只有 5 分钟，你能向自己解释清楚为什么要做这个功能吗？** 如果不能，PRD 可能需要更聚焦。

2. **6 个月后的自己看这个 PRD，能理解当时的决策吗？** PRD 应该记录"为什么"，而非只记录"是什么"。

3. **这个 PRD 能用一个原型替代吗？** 对于 UI 和交互密集的功能，原型可能比文字更高效。

4. **如果 AI 可以帮你写代码，你还需要写什么？** PRD 写作能力可能是 AI 时代最重要的产品技能。
