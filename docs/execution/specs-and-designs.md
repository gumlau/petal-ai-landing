# 规格与设计文档写作指南 - Petal GTD 应用分析

> 对应技能：`.claude/skills/writing-specs-designs/SKILL.md`

## 概述

规格文档（Spec）和设计文档（Design Doc）是将产品需求转化为可执行方案的关键桥梁。对于 Petal GTD 这样的独立开发项目，这些文档的核心价值不在于形式上的完整，而在于**帮助开发者在动手之前理清技术实现路径，减少返工和重构**。

本文档基于 7 位产品领导者的 10 条洞察，探讨低保真设计与高保真设计的权衡，提供适合独立开发的设计流程，并讨论何时需要详细规格、何时直接编码。

## 核心原则

基于 `.claude/skills/writing-specs-designs/SKILL.md` 的核心洞察：

### 1. 低保真草图驱动协作

> "如果我在白板上画得很糟糕，其他人会说，'不不不，不是这样的。给我笔。' 这让你很快达成共同愿景。" —— Christina Wodtke

低保真的价值在于**邀请参与**：

- 完美的高保真设计暗示"这已经定稿了"，阻止他人提出修改意见
- 故意"画得不好"反而激发他人参与和纠正
- 对于独立开发者：在白板或 iPad 上快速涂鸦，比在 Figma 中花几小时更有效
- 核心洞察：低保真不是"偷懒"，而是**刻意的沟通策略**

### 2. 良好的规格文档澄清而不过度规定

> "Shaping 会议的产出是某种图或示意图，工程师、产品和设计看了之后都会说，'我完全知道要构建什么了。'" —— Ryan Singer

规格文档的目标是"适度详细"：

- 过于简略：团队无法理解要做什么
- 过于详细：限制了实现的灵活性，浪费时间在不重要的细节上
- 理想状态：描述"墙内的电线"——技术可行性清晰，但不规定每个按钮的颜色

Ryan Singer 的标准：一个好的规格应该只包含 **10 个或更少的"活动部件"**（moving pieces）。

### 3. 通过原型感受产品

> "我无法告诉你这能不能工作。我必须感受它。我必须试用它。静态设计稿无法告诉你它会是什么感觉。" —— Tamar Yehoshua

原型比文档更能揭示问题：

- 静态设计稿无法展示交互流畅度、加载等待体验、手势反馈
- 真实数据的原型比假数据更有说服力
- 对于独立开发者：花 1 天做个粗糙原型，胜过花 1 周写详细规格

### 4. 代码原型优于静态设计稿

> "我们不再在静态设计稿的设计探索上花费那么多周期，而是问，'我们能多快进入真实软件中进行原型开发，即使它很乱、会扔掉？'" —— Noah Weiss

代码原型的优势：

- 可以真正"感受"交互，而非想象
- 揭示技术可行性问题
- Slack 团队的经验：用"乱而可扔弃"的代码快速验证想法

对于独立开发者：与其在 Figma 中精心设计，不如用 v0/Replit 快速生成可交互的代码原型。

### 5. 产品存活于像素之中

> "你应该设计层级、像素、流程，所有东西。这是你的责任。产品成败在于像素。" —— Nikita Bier

对于 0 到 1 的产品，细节决定成败：

- 信息层级是否清晰？
- 用户流程是否顺畅？
- 每一个点击是否提供即时价值？

独立开发者的优势：你可以既是产品设计者，又是像素级执行者，无需在设计和开发之间传递损耗。

### 6. 优化每一次点击

> "移动应用上的每一次点击对产品开发者来说都是奇迹。用户会很快转向下一个应用。" —— Nikita Bier

设计时的极致效率思维：

- 每个交互都必须提供即时价值
- 观察用户如何使用手机——他们在应用间快速切换
- 对于 GTD 应用：快速捕获的"摩擦"决定用户是否会使用

### 7. 使用粗笔草图

> "使用面包板和粗笔草图。我们要点击这个按钮，从这个按钮到这里，这个计算运行，然后得到这个答案。" —— Ryan Singer

粗笔草图的价值：

- 物理上阻止你画太多细节
- 强迫你聚焦于"元素"（affordances）和"连接"（connections）
- 避免陷入颜色、间距等无关紧要的讨论

### 8. 临时捷径会变成永久

> "临时设计捷径往往会变成产品的永久遗产，贯穿多次技术重写。" —— Tom Conrad

这是一个严肃的警告：

- 你认为"以后再改"的临时方案，可能会存在 30 年
- 用户会习惯早期的交互模式，即使技术完全重写
- 对于 Petal GTD：今天做的 UI 决策，可能定义未来多年的用户预期

### 9. PM 应该学会草图

> "学习如何草图，学习 Balsamiq。能够在概念层面思考 UI 和 UX 如何工作，是成为 PM 的关键技能。" —— Ravi Mehta

对于独立开发者，这意味着：

- 不需要成为专业设计师，但需要能快速表达想法
- 工具推荐：Balsamiq（线框图）、Excalidraw（手绘风格）、iPad + Pencil
- 核心能力：能在 5 分钟内画出一个功能的核心流程

## Petal GTD 现状分析

### 低保真 vs 高保真设计的权衡

对于 Petal GTD 当前阶段，设计保真度应该根据场景灵活选择：

**适合低保真设计的场景**：
- 探索新功能方向时（如 Focus Mode 概念验证）
- 需要快速验证多个方案时
- 与自己"对话"理清思路时
- AI 辅助头脑风暴时

**适合高保真设计的场景**：
- 核心交互已确定，需要精打磨时
- 涉及动画、过渡等微交互设计时
- 准备 App Store 截图等营销材料时
- 需要与 Things 3 等竞品做像素级对比时

### 适合独立开发的设计流程

对于独立开发者，推荐以下流程：

```
想法 → 粗笔草图（5分钟）→ 代码原型（1小时-1天）→ 迭代 → 正式开发
```

**关键点**：

1. **跳过 Figma 阶段**：对于独立开发者，直接从草图到代码往往更快
2. **用 v0/Replit 生成原型**：AI 工具让代码原型的门槛大幅降低
3. **在真机上测试**：GTD 应用的体验必须在真机上感受
4. **记录关键决策**：为什么选择这个方案？放弃的方案有什么问题？

### 何时需要详细规格，何时直接编码

**需要详细规格的情况**：

| 场景 | 原因 |
|------|------|
| 涉及数据模型变更 | 数据结构一旦发布，变更成本极高 |
| 涉及多个组件协作 | 需要明确接口和边界 |
| 未来可能扩展的功能 | 需要考虑扩展性设计 |
| 核心交互流程变更 | 影响用户习惯，需要慎重 |

**可以直接编码的情况**：

| 场景 | 原因 |
|------|------|
| UI 样式调整 | 视觉调整可以在代码中快速迭代 |
| 已有模式的复用 | 只是套用现有组件和流程 |
| 小 bug 修复 | 问题清晰，解决方案明确 |
| 实验性功能 | 快速验证想法，失败成本低 |

### Petal GTD 设计决策案例

以"Today 视图"为例，分析设计决策过程：

**问题定义**：
- 用户需要快速看到今天要做什么
- 避免信息过载造成焦虑

**设计方案对比**：

| 方案 | 优点 | 缺点 | 决策 |
|------|------|------|------|
| A. 平铺所有任务 | 信息完整 | 容易焦虑 | ❌ |
| B. 只显示 3 个任务 | 聚焦 | 遗漏其他任务 | ❌ |
| C. 分组 + 折叠 | 平衡完整和聚焦 | 交互复杂 | ✅ |

**选择方案 C 的原因**：
- 符合"心智像水"的愿景（见 `docs/product-strategy/product-vision.md`）
- 用户可以控制信息密度
- 与 Things 3 的设计逻辑一致

## 关键洞察

### 洞察 1：设计文档的目的是减少返工

好的设计文档不是为了"正式"，而是为了：
- 在写代码之前发现问题
- 避免"写到一半发现方向错了"
- 给未来的自己留下决策依据

如果写完设计文档后，你对实现路径更清晰了，它就是成功的。

### 洞察 2：原型验证胜过文档评审

传统流程：写详细设计文档 → 评审 → 修改 → 再评审 → 开始开发

更有效的流程：粗略草图 → 快速原型 → 真机测试 → 记录关键决策 → 开始开发

对于独立开发者，后者显著更快。

### 洞察 3：设计保真度应该渐进提升

- **第 1 轮**：粗笔草图（5 分钟），验证方向
- **第 2 轮**：代码原型（1-4 小时），验证交互
- **第 3 轮**：正式开发，逐步打磨

不要在第 1 轮就追求像素级完美。

### 洞察 4：临时方案的代价被低估

Tom Conrad 的警告值得深思：
- 你今天随手做的 UI 决策，可能会陪伴产品 10 年
- 用户会习惯你的"临时"设计，即使你内心知道它不完美
- 对于核心交互，值得在第一次就做对

### 洞察 5：独立开发者的设计优势

独立开发者在设计上有独特优势：
- **无传递损耗**：你就是设计师和开发者，不需要"交接"
- **快速迭代**：想法可以立即实现，无需等待设计评审
- **一致性**：整个产品由一个人的审美标准驱动
- **深度同理**：作为重度用户，你最懂用户痛点

## 行动建议

### 适合独立开发者的设计规格模板

```markdown
# [功能名称] 设计规格

## 问题回顾
- 解决什么用户问题？（链接到 PRD）
- 为什么现有方案不够好？

## 核心交互
```
[粗笔草图或 Excalidraw 截图]
```

用户流程：
1. 用户做 X
2. 系统响应 Y
3. 用户看到 Z

## 关键决策

### 决策 1: [描述]
- 方案 A: ...
- 方案 B: ...
- **选择**: A，因为 ...

### 决策 2: [描述]
- ...

## 技术实现要点
- 数据模型变更（如有）
- 需要新增的组件
- 潜在风险点

## 原型
- [链接到 v0/Replit 原型]
- [真机测试录屏，如有]

## 验收标准
- [ ] 条件 1
- [ ] 条件 2
```

### 短期行动（1-2 周）

1. **建立设计习惯**
   - 任何新功能，先用 5 分钟画粗笔草图
   - 在 iPad 或纸上，不用追求工具

2. **尝试 AI 原型工具**
   - 用 v0.dev 生成 UI 原型
   - 用 Replit 快速验证交互逻辑

3. **在真机上测试**
   - 每个新交互都在真机上感受
   - 记录"这里感觉不对"的地方

### 中期行动（1-2 月）

1. **建立设计决策记录**
   - 创建 `docs/design-decisions/` 目录
   - 记录关键 UI 决策的"为什么"

2. **对比竞品体验**
   - 定期使用 Things 3、Todoist 等竞品
   - 记录"这个交互比我们好"的地方
   - 分析原因，决定是否借鉴

3. **回顾"临时"设计**
   - 检查代码中标注为 "TODO: 改进" 的 UI 部分
   - 决定哪些需要正式处理

### 长期行动（季度）

1. **建立设计系统**
   - 整理常用的颜色、间距、组件
   - 确保一致性，减少每次决策成本

2. **设计评审复盘**
   - 每季度回顾：哪些设计决策是成功的？
   - 哪些"临时方案"变成了永久设计？
   - 迭代设计流程

## 思考问题

1. **这个功能，你能用 5 分钟的草图解释清楚吗？** 如果不能，说明思路还不够清晰，不应该开始写代码。

2. **你愿意在真机上每天使用这个交互吗？** 作为重度用户，你的直觉是最好的设计验证。

3. **这个"临时"设计，你愿意它存在 5 年吗？** 如果不愿意，现在就值得多花时间做对。

4. **如果有 1 小时，你选择画更精细的设计稿，还是做个粗糙原型？** 大多数情况下，后者更有价值。

5. **这个设计决策需要记录下来吗？** 如果未来可能回头问"当时为什么这样设计"，就应该记录。
